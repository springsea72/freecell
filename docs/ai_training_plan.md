# AI Training Plan 5.0

This document freezes the first AI policy training design before any training code is added. It is intended to guide the 5.1 implementation thread while keeping the current project runnable without mandatory ML dependencies.

## Current Project Capabilities

- Rule model: `game_model.py` owns cards, move types, legal move generation, move validation, `apply_move()`, stable `state_key()`, win/terminal checks, clone support, sequence movement, and automatic home moves.
- CLI game: `main.py` lets a user inspect the current state, list legal moves, and execute moves through the model layer.
- Solver: `solver.py` provides bounded heuristic search and returns `SolveResult` with a replayable move path and search statistics. It does not modify the input game.
- Trace I/O: `trace_io.py`, `autoplay.py`, and `replay.py` save, load, and verify solved JSON traces from reproducible seeds.
- Dataset builder: `dataset_builder.py` converts solved traces into JSONL samples. Each sample captures the pre-action state, legal action set, trace action, and `action_index`.
- Baselines: `policy_baseline.py` evaluates non-trained `first_legal` and hand-written `heuristic` policies on JSONL samples.
- Policy player: `policy_player.py` runs baseline policies directly in `FreeCellGame(seed=...)`, with loop detection and max-step limits.
- Report: `report.py` aggregates solver benchmark, JSONL policy accuracy, and direct policy-player metrics.
- GUI: `gui.py` supports normal play, solver path playback, pause/resume/stop, playback speed, save trace, and load verified trace playback. Policy player and future model policies are not connected to GUI.

## First AI Goal

The first AI policy should be a supervised imitation policy.

- Input: JSONL produced by `dataset_builder.py`.
- Target: choose the trace action from the current legal move set.
- Training objective: maximize accuracy of selecting `sample["action_index"]` among `sample["legal_moves"]`.
- Scope: offline policy training and evaluation only. It should not change game rules, solver behavior, trace schema, dataset schema, or GUI behavior.

## Data Contract

Each JSONL row is one decision point from a solved trace.

- `version`: dataset row schema version.
- `source_trace`: source trace file name or path label.
- `seed`: FreeCell seed used to create the trace.
- `step_index`: zero-based index of the decision inside the trace.
- `remaining_moves`: number of moves remaining from this state including the target action.
- `state`: action-before game state.
  - `columns`: eight tableau columns, each card encoded as `{"suit": "SPADES", "value": 7}`.
  - `free_cells`: four entries, each card dict or `null`.
  - `home_cells`: suit-name keys with ordered home stacks.
- `legal_moves`: legal moves generated by `FreeCellGame.generate_legal_moves()` at this state.
- `action`: the move from the solved trace at this state.
- `action_index`: index into `legal_moves` where `legal_moves[action_index] == action`.
- `progress`: optional progress labels computed by applying `action` on a clone:
  - `home_cards`: cards in home cells before action.
  - `home_cards_after`: cards in home cells after action.
  - `home_delta`: immediate home-card gain.
  - `remaining_moves`: same value as the top-level field.
  - `remaining_moves_after`: remaining trace moves after the action.
  - `won_after`: whether the cloned state is won after the action.

Training must use an action mask. The model may score candidate moves, but the final action must always be selected from `legal_moves`. It must never emit an arbitrary move outside `game.generate_legal_moves()`.

The `progress` field is additive. Existing JSONL rows without it remain valid for the current feature extraction and imitation trainer.

Invalid samples should be rejected during dataset loading or smoke validation:

- `action_index` out of bounds.
- `action` not equal to `legal_moves[action_index]`.
- Missing state fields or unsupported schema version.
- Empty `legal_moves` for a non-terminal training row.

## Minimal Feature Design

The first implementation should favor simple, deterministic feature extraction over model complexity.

State features:

- Card location for each of 52 cards:
  - one of 8 columns with depth index,
  - one of 4 free cells,
  - one of 4 home cells,
  - or absent only if input validation fails.
- Home progress per suit: top home value from 0 to 13.
- Next home value per suit, encoded as the next card rank that can be moved home.
- Free-cell occupancy: four binary values plus total free cells used/free.
- Column features:
  - length of each column,
  - top card suit/value/color if present,
  - movable suffix length if easy to derive from state,
  - whether each column has a buried low card such as A/2/3,
  - empty-column indicator.
- Global features:
  - total home cards,
  - number of empty columns,
  - number of occupied free cells,
  - `remaining_moves` if present.

Candidate move features:

- Move type one-hot: `FREE_TO_HOME`, `COL_TO_HOME`, `FREE_TO_COL`, `COL_TO_COL`, `COL_TO_FREE`.
- `from_idx`, `to_idx`, and `count`.
- Source and destination type indicators.
- Moving card value/suit/color if derivable from state.
- Destination top card value/suit/color for column moves if present.
- Booleans for home move, free-cell release, source-column emptied, target-column empty, and multi-card sequence.
- Feature version 2 adds action-effect indicators for increasing home cards, exposing buried A/2/3, emptying the source column, occupying or releasing a free cell, moving to an empty column, reducing immediate buffer space, and moving a card near current home progress.

Recommended first architecture:

- Encode state into a fixed numeric vector.
- Encode each candidate move into a fixed numeric vector.
- Score each candidate independently with a small MLP over `[state_features, move_features]`.
- Apply an action mask over the candidate list and choose the highest legal score.

This keeps the output space dynamic and naturally tied to legal moves.

## Model Interface Draft

Future model modules should expose a small interface that mirrors the existing baseline and player tools.

Suggested public functions:

- `load_model(path, device=None) -> object`
- `choose_action(game, model, device=None) -> Move`
- `score_legal_moves(game, model, device=None) -> list[tuple[Move, float]]`

Requirements:

- `choose_action(game, ...)` must call `game.generate_legal_moves()`.
- The returned `Move` must be one of the generated legal moves.
- The policy must execute moves through `game.apply_move(move)` in callers.
- The model interface must not mutate `game` while scoring.
- Serialization should include enough metadata to validate feature version and model type.

The first model policy should integrate with offline evaluation and `policy_player.py` style direct play before any GUI integration is considered.

## Dependency Strategy

PyTorch is the recommended optional training dependency for 5.1 because it is widely available, supports CPU training, and can later use GPU acceleration without changing model code.

Rules:

- Do not add PyTorch or other ML packages as required dependencies for normal gameplay, solver, benchmark, dataset building, or GUI.
- Keep training imports inside future training/model modules, not in core modules.
- Do not add CUDA, ROCm, or GPU-specific packages to a main requirements file.
- If a future optional requirements file is added, keep it clearly named, for example `requirements-ml.txt`.
- The repository must continue passing current non-ML tests without installing ML dependencies.

## Device Strategy

Training and inference code in 5.1 should auto-select a device:

- Prefer GPU only when the installed ML library reports one as available.
- Fall back to CPU by default.
- CPU must support a tiny smoke train/evaluate run in environments without a discrete GPU.
- Do not hard-code CUDA or ROCm assumptions in paths, flags, or model code.
- Log the selected device in training output for reproducibility.

## Artifact Strategy

Generated artifacts should not be committed by default.

Ignored outputs include:

- `models/`
- `checkpoints/`
- `*.pt`
- `*.pth`
- `*.onnx`
- `traces/`
- `datasets/`
- `reports/`
- local JSONL and temporary trace files.

The repository should commit:

- source code,
- tests,
- documentation,
- small fixed seed lists such as `benchmarks/seeds.txt`,
- small hand-written fixtures only when they are stable and useful.

Training logs, checkpoints, exported models, generated datasets, generated reports, and bulk traces should remain local unless a later task explicitly creates a small fixture with a clear reason.

## 5.1 Acceptance Criteria

Minimum training implementation should provide:

- A small training CLI that consumes `dataset_builder.py` JSONL.
- Reproducible seed control for Python and the selected ML library.
- CPU smoke training on a tiny dataset.
- Train/validation split or explicit train/eval input support.
- Saved model artifact in an ignored path such as `models/`.
- Offline accuracy output comparable to `policy_baseline.py`.
- A model-loading path that can score candidate legal moves.
- Tests that can run without mandatory GPU access.
- No changes to game rules, solver search semantics, trace schema, dataset schema, or GUI behavior.

Recommended smoke flow for 5.1:

1. Generate or provide a tiny JSONL dataset from existing trace tooling.
2. Train for a very small number of epochs on CPU.
3. Save a model under `models/`.
4. Reload the model.
5. Report sample count, loss, and accuracy.
6. Confirm selected actions are always masked to legal moves.

## 5.2 Acceptance Criteria

Model policy evaluation should provide:

- Offline evaluation against JSONL samples using the same action-mask rule.
- Direct play evaluation on `FreeCellGame(seed=...)`, similar to `policy_player.py`.
- Metrics compatible with `report.py` style output:
  - games,
  - wins,
  - win rate,
  - average steps,
  - average home cards,
  - loop/max-step/terminal reasons.
- No GUI integration yet.
- No solver fallback hidden inside model policy evaluation.
- No changes to game rules or trace/dataset contracts.

The 5.2 evaluation entry point is expected to be `learned_policy_eval.py`, with:

- JSONL dataset action accuracy mode.
- Direct seeded play mode.
- Actions selected only from `game.generate_legal_moves()`.
- Execution only through `game.apply_move(move)`.
- No GUI connection.

Direct play evaluation may apply a small, explainable inference-time rerank over the model-scored legal moves to prefer home moves and resource-releasing moves when model scores are close. This rerank must not affect JSONL dataset accuracy, training, or dataset generation.

JSON reports should keep learned-policy per-seed play results, including terminal reason and home progress, so experiment artifacts can be audited without rerunning model inference. Text reports may remain summary-only.

## 5.1 Implementation Notes

The minimal 5.1 training loop is expected to live in separate optional modules:

- `policy_features.py`: standard-library feature extraction and sample validation.
- `learned_policy.py`: optional PyTorch model loading, legal-move scoring, and masked action selection.
- `train_policy.py`: optional PyTorch training CLI.
- `requirements-ml.txt`: optional ML dependency list.

Normal project commands must continue to work without installing `requirements-ml.txt`. Future evaluation tooling should import model code only when explicitly evaluating a learned policy.

The current minimal trainer exposes `--hidden-size`, `--batch-size`, `--lr`, `--validation-split`, `--seed`, and `--device`. `hidden_size` is stored in model metadata so saved checkpoints can be loaded with the same architecture, and `batch_size` controls optimizer step frequency through batch loss accumulation.

The experiment orchestrator writes all generated traces, datasets, models, reports, and `manifest.json` under the requested output directory. The manifest records experiment parameters, seed range, solved trace count, dataset sample count, generated paths, and training summary. These generated artifacts remain ignored by git.

## Explicitly Out of Scope

- Reinforcement learning.
- Self-play.
- Large-scale training.
- Distributed training.
- GUI model playback.
- Changing `game_model.py` rules.
- Changing solver search semantics.
- Replacing existing heuristic baselines.
- Adding mandatory ML dependencies to normal project workflows.
